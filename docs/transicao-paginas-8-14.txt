      "status": "accepted"
  }




6. Regras de segurança e operação
A API deve ser tratada como uma superfície de ingestão externa. O token deve ser
específico por ambiente e, idealmente, específico por prefeitura ou origem. A próxima
versão deve substituir o mapa em memória usado no protótipo por banco persistente,
aplicar limite de requisições, registrar IP e user-agent quando permitido, calcular checksum
do corpo e definir política de retenção para cargas brutas.
O payload recebido não deve ser executado como código. Campos livres devem ser
armazenados como dados JSON, com limites de tamanho e profundidade. O servidor deve
rejeitar cargas acima do tamanho operacional estabelecido, validar datas e impedir que
 tenantId enviado pelo remetente permita acesso a outra prefeitura sem autorização
previamente cadastrada.
A validação do token confirma a origem técnica, mas não substitui a autorização comercial
da Betha. O fluxo real depende de a Betha aceitar o domínio, método, headers, formato e
processo de envio do Painel Municipal.

                                                                e escopo por origem

7. Dashboard web e experiência do usuário
A interface web deve usar um shell administrativo persistente. No desktop, a sidebar deve
conter a marca, descrição curta do sistema, navegação principal e um cartão de ambiente.
No mobile web, a navegação deve se transformar em uma barra ou menu compacto sem
esconder o conteúdo principal.
A paleta visual já definida usa azul petróleo e verde-água como sinais de operação e
sucesso, azul vivo para ações primárias, laranja para atenção e superfícies claras para
leitura de indicadores. A hierarquia deve privilegiar números grandes, títulos curtos,
unidade de medida explícita, período de referência e estado de atualização.
Os dashboards não devem apresentar números demonstrativos como se fossem produção.
Quando a API não tiver dados para um período, o componente deve exibir estado vazio ou
desconhecido. Cada indicador deve carregar metadados mínimos: origem, última
atualização, período, qualidade e status de processamento.

8. Importação JSON/CSV
O protótipo permitiu selecionar arquivos JSON e CSV e validar a extensão. No novo projeto
web, a importação deve evoluir para um fluxo de quatro passos: seleção do arquivo, leitura
e prévia, validação de colunas e confirmação da carga.
A tela deve mostrar o nome, tamanho, tipo, quantidade de linhas, colunas reconhecidas,
linhas inválidas, campos obrigatórios ausentes e ação de confirmação. A importação não
deve gravar diretamente no banco sem criar um ingestion_batch e um recibo de
processamento.
  Plain Text
  Arquivo selecionado
    -> leitura segura no navegador
    -> prévia limitada
    -> validação de schema por resource
    -> criação de lote
    -> processamento assíncrono
    -> recibo, erros e métricas

Não solicitar nem armazenar credenciais Betha antes da validação comercial. Quando o
setor comercial fornecer o método de autenticação, o endpoint oficial, o Swagger e os
requisitos de user-access , registrar essas informações em documentação versionada e criar
secrets específicos para produção.

11.1 Definição de pronto
Uma tarefa só deve ser considerada pronta quando possuir implementação, teste
automatizado correspondente, estado de erro e documentação mínima. Nenhum
componente deve exibir mock como dado oficial. Toda integração externa deve possuir
contrato, autenticação, timeout, tratamento de erro e estratégia de reprocessamento.

12. Pendências explícitas
As principais pendências não são bugs da interface; são dependências de integração e
produção. Ainda é necessário obter o Swagger oficial da Betha, confirmar se a Betha
enviará dados para um endpoint externo do município, confirmar o formato de
autenticação, definir o user-access , validar o domínio receptor e estabelecer a política
comercial de habilitação.
Também devem ser concluídos o banco persistente dos recebimentos, a autenticação dos
usuários do painel, as permissões por prefeitura, o histórico de auditoria, o processamento
assíncrono e a observabilidade operacional.
  Regra de não invenção: até que a Betha forneça o contrato oficial, o sistema deve
  documentar apenas o envelope receptor próprio e manter records como objeto aberto.
  Não criar campos específicos de tributos, contribuintes, imóveis ou débitos com base em
  suposição.
